# 角色化数据看板设计

日期：2026-10-12

状态：已确认

范围：学院管理员、方向负责人、学生首页
目标：把首页从通用卡片堆叠改成有明确业务洞察的角色化数据看板。

## 1. 背景与目标

当前首页如果只是展示功能卡片，用户需要自己打开多个页面才能判断人员、报告、评分、积分和 OJ 考核是否正常。首页应成为各角色的日常工作入口：

- 学院管理员看到全院规模、活跃度、评分/复核队列、风险成员和方向对比。
- 方向负责人看到本方向学生、报告完成情况、待处理事项和方向排名。
- 学生看到自己的积分、排名、报告状态、待办和最近动态。

目标是信息密度更高、状态更清楚、操作路径更短，而不是把 API 数据重新排成更多相同卡片。

## 2. 范围与非目标

### 范围

- 三个角色分别提供首页数据聚合接口和对应前端看板。
- 复用现有成员、报告、积分、排行榜、OJ 考核和审计数据。
- 为前端提供稳定的时间范围、趋势、分组、状态和待办数据。
- 保留现有页面和 API，不删除日报、周报、积分流水、排行榜或 OJ 明细入口。

### 非目标

- 不改变日报/周报评分规则、积分规则、自动移出规则或 OJ 评分优先级。
- 不把原始报告正文、代码、私有测试数据、模型原始输出、密码、Token 放进看板。
- 不在前端重新计算排行榜名次、成员总数或自动移出时间。
- 不实现 BI 数据仓库、跨学院报表中心或复杂报表导出。

## 3. 角色首页

### 3.1 学院管理员 Dashboard

接口草案：

```http
GET /api/v1/dashboard/admin?range=7d|30d
```

数据分区：

1. `overview`
   - 学生总数、`ACTIVE` 学生数、方向负责人数量、已移出学生数。
   - 今日日报提交数、近 7/30 天日报完成率、本周周报完成率。
   - 待 AI 评分、评分失败、待人工复核数量。
   - OJ 考核数量、已发布考核数量、待判定提交数量。
2. `trends`
   - 近 7/30 天每天日报提交量、评分完成量、有效积分变化量。
   - 趋势按 `Asia/Shanghai` 业务日期聚合。
3. `directions`
   - 每个方向的 `ACTIVE` 学生数、日报完成率、周报完成率、平均积分、待处理数量。
   - 只展示方向级聚合，不展示学生联系方式或报告正文。
4. `attention`
   - 评分失败、待人工复核、不活跃风险学生、待判定 OJ 提交。
   - 风险列表只返回 memberId、展示名、方向、最近日报日期、建议处理状态。
5. `recentActivity`
   - 脱敏审计事件、最近加入/恢复、最近发布考核。
   - 不返回密码、Token、报告全文、代码或模型原始响应。

### 3.2 方向负责人 Dashboard

接口草案：

```http
GET /api/v1/dashboard/leader?range=7d|30d
```

只聚合当前用户获授权方向；无授权方向时返回空数据和 0 总数，不泄露其他方向。

数据分区：

1. `overview`
   - 本方向 `ACTIVE` 学生数、今日日报提交数、近 7/30 天日报完成率、本周周报完成率。
   - 本方向积分总量、待 AI/人工处理数量、待判定 OJ 提交数量。
2. `students`
   - 学生列表：memberId、展示名、当前状态、最近日报、最近周报、积分、方向排名。
   - 不包含学号、联系方式或报告正文。
3. `trends`
   - 本方向近 7/30 天日报提交量、评分完成量、积分变化量。
4. `attention`
   - 未提交日报学生、评分失败、待复核、待判定 OJ、不活跃风险。
5. `rankingPreview`
   - 本方向排行榜前 10 名，仅 `ACTIVE` 学生；负责人自己不进入排行榜。

### 3.3 学生 Dashboard

接口草案：

```http
GET /api/v1/dashboard/student?range=7d|30d
```

数据分区：

1. `overview`
   - 当前累计积分、总排名、方向排名、当前日报/周报状态、下一个日报截止状态。
   - 方向负责人不使用此接口；本接口仅面向 `STUDENT`。
2. `progress`
   - 最近 7/30 天积分变化、日报/周报提交完成度、连续提交状态。
   - 连续提交只展示状态，不在前端自行推断自动移出。
3. `reports`
   - 最近日报/周报状态、评分状态、最近提交时间、是否可编辑。
   - 不返回他人报告，也不把 AI 原始输出返回给前端。
4. `assessments`
   - 可参加/已结束的 OJ 考核摘要、本人提交状态、最终结果状态。
   - 不返回代码正文、私有测试数据或 OJ 原始输出。
5. `points`
   - 最近积分流水摘要和查看完整流水入口。
6. `rankingPreview`
   - 个人总排名和方向排名摘要，不显示其他学生敏感资料。

## 4. 后端接口与数据边界

### 4.1 API 风格

- 路径：`/api/v1/dashboard/admin`、`/api/v1/dashboard/leader`、`/api/v1/dashboard/student`。
- 统一响应：`code/message/data`，错误码沿用现有 `INVALID_REQUEST/UNAUTHORIZED/FORBIDDEN/NOT_FOUND/SERVICE_UNAVAILABLE`。
- `range` 仅支持 `7d`、`30d`，默认 `30d`。
- ID 一律为十进制字符串。
- OpenAPI 先标记 `planned`，实现并通过契约测试后改为 `implemented`。
- 三个接口都要求 Bearer 会话；学院管理员、获授权方向负责人、学生分别调用对应接口。

### 4.2 服务结构

建议新增独立的 dashboard 查询服务，不把聚合 SQL 塞进现有 Controller：

- `DashboardController`
- `DashboardAdminService`
- `DashboardLeaderService`
- `DashboardStudentService`
- `DashboardQuerySupport`

复用现有：

- `SessionPrincipal`
- `MemberScopePolicy`
- `PointsPolicy`
- `InactivityPolicy`
- `DatabaseSchemaGuard`
- `OjAdapter` 领域结果的安全摘要

所有聚合先在 SQL/数据库查询层做权限过滤，再分页或截断列表，禁止先查全院再在内存过滤后返回错误 `total`。

### 4.3 数据来源

- 成员状态、方向、加入/恢复时间：`member`、`direction`。
- 报告提交状态和版本：`report`、`report_version`。
- 积分：`point_ledger` 净和；排行榜复用现有学生排名查询。
- OJ：`assessment`、`assessment_submission`、`assessment_result` 的安全状态和计数。
- 审计：`assessment_audit`、`audit_log` 的脱敏摘要。

### 4.4 安全要求

- 学院管理员可看全院聚合和安全的待办列表。
- 方向负责人只能看授权方向。
- 学生只能看本人数据和公开排名摘要。
- 看板响应不得出现：报告全文、代码正文、私有测试数据、原始模型输出、API Key、密码、Token、联系方式、学号。
- 看板聚合不得写入 `point_ledger`、修改报告状态、触发自动移出或改变 OJ 结果。

## 5. 前端视觉与交互

采用“运营看板 + 明细入口”的结构，不采用整页同尺寸卡片墙。

### 5.1 共用布局

- 顶部：角色化标题、时间范围切换、最近更新时间、刷新按钮。
- 主体左侧：趋势图或方向对比；右侧：需要处理的事项。
- 底部：排行榜/最近动态/最近报告，保留进入完整列表的入口。
- 使用表格、趋势线、横向条形图、状态标签和进度指标表达数据。
- 每个图表提供文本摘要或可访问的数据表，不只依赖颜色。
- 加载使用稳定 skeleton；空数据提供下一步操作，不留大面积空白。
- 移动端允许表格横向滚动或切换成摘要行，不破坏 375px 布局。

### 5.2 风格边界

- 采用简洁、网格化、数据优先的企业后台风格。
- 颜色只表达状态和优先级，不用大面积渐变、玻璃拟态或装饰性 AI 风格。
- 重点数据用字重、位置、线条和对比表达，不做大量浮动圆角卡片。
- 使用 SVG 图标；不用 emoji 作为界面图标。
- 动效只用于加载、切换和状态反馈，遵守 `prefers-reduced-motion`。

## 6. 测试与验收

### 6.1 后端

- 三个接口的角色矩阵测试。
- 方向负责人跨方向聚合不泄露数据。
- 学生只能获得本人数据。
- 排行榜人数、rank、同分跳位只统计 `ACTIVE` 学生，方向负责人不计入。
- 报告、积分、OJ 聚合与现有明细接口一致。
- 看板读取不会写积分、不会修改报告、不会触发移出。
- 响应不包含代码、报告全文、联系方式、学号、Token 或原始 Provider 输出。
- OpenAPI 契约、分页/总数和错误码测试。

### 6.2 前端

- 三种角色的首页布局和导航权限正确。
- 时间范围切换只发起一次对应接口请求。
- loading、empty、error、无权限状态均有明确反馈。
- 图表可读、可键盘访问，图表旁有数据摘要/表格。
- 375px、768px、1024px、1440px 均不横向溢出页面主体。

## 7. 实施顺序

1. 先冻结三个 dashboard DTO 和角色权限到 OpenAPI。
2. 实现管理员聚合接口，校验报表、评分、风险和方向数据。
3. 实现负责人范围聚合接口。
4. 实现学生个人聚合接口。
5. 前端分别完成管理员、负责人、学生看板，不复用不合适的卡片布局。
6. 契约、权限、隐私和视觉验收后再把接口状态改为 `implemented`。

## 8. 已确认决策

1. 管理员首页包含 OJ 考核数据。
2. 管理员首页默认时间范围为 `30d`，方向负责人和学生默认为 `7d`。
3. 不活跃风险列表只展示前 10 条并提供跳转，不在首页直接暴露全部名单。
