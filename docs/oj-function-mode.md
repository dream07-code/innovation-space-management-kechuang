# OJ 函数式判题（力扣风格）

题目可以按两种方式判题，创建或编辑题目时在「判题方式」里选择。

| 模式 | 学员写什么 | 测试点输入 | 判题 |
| --- | --- | --- | --- |
| 命令行读写（STDIO，默认） | 完整程序，从标准输入读到标准输出 | 程序的标准输入原文 | Judge0 直接比对输出 |
| 函数传参（FUNCTION） | 只写函数，不写 `main` | JSON 参数数组，例如 `[10]`、`[[2,7,11,15],9]` | 后端按签名生成调用桩，调用学员函数并比较返回值 |

## 支持的签名

- 参数最多 4 个，类型与返回类型限于：
  `int`、`long`、`bool`、`string`、`int[]`、`long[]`、`string[]`、`int[][]`
- 返回值为数组时，判题按紧凑 JSON 比较，例如 `[1,2]`；字符串带引号，例如 `"abc"`；
  布尔为 `true` / `false`。
- 期望输出写返回值本身即可（`55`、`[1,2]`），后端会先归一化成紧凑 JSON 再比对。

## 各语言骨架

选择函数模式后，编辑器按题目签名生成骨架，学员只填函数体：

```cpp
class Solution {
public:
    long long fib(long long arg0) {
        // 在此实现
    }
};
```

```java
class Solution {
    public long fib(long arg0) {
        // 在此实现
    }
}
```

- Java 的主类是 `Main`，由判题系统追加；学员的类必须叫 `Solution` 且不要写 `public`。
- Go 不写 `package` 与 `main`，只写函数，判题系统会补齐。
- Rust 自带 `struct Solution;` 与 `impl Solution`，只填方法体。

## 判题流程

1. 读取题目签名与测试点参数；
2. 对每个测试点，把参数以字面量形式嵌进入口代码（例如 `Solution().fib(10)`）；
3. 逐个提交 Judge0，合并逐点结果（通过数、最长耗时、最大内存、首个失败判定）；
4. 期望输出按紧凑 JSON 归一化后比较。

因为每个测试点单独提交，编译错误会在每个测试点上重复出现，与命令行模式的编译行为一致。

## 结果与代码可见性

- 正式考核提交后，学员能看到**一个参考测试点**的输入、实际输出和期望输出
  （优先从失败的测试点里按提交号稳定挑选），其余测试点保持隐藏。
- 管理员和方向负责人可以在考核结果页点「代码」查看提交源码；提交详情和人工批阅页
  也直接展示只读代码，方便人工评分。查看非本人代码会写入审计记录。
- 输入/实际输出/期望输出都截断到 2000 字符后存储，接口不会返回完整判题日志。

## 已有题库不用重新导入

V10 迁移用 `ADD COLUMN ... NOT NULL DEFAULT 'STDIO'` 加字段，已有题目自动成为
命令行模式，题目、测试点、考核与题目的关联都保持原样，**不需要重新导入题库**。

把某道老题改成函数式，有两种方式：

1. 题目编辑页把「判题方式」切到函数传参，填函数名与签名，再把每个测试点的输入
   从原来的程序输入改写成 JSON 参数数组，保存即可（题目版本 +1）。
2. 调 `PATCH /api/v1/assessment-problems/{id}`，请求体至少包含
   `judgeMode`、`functionName`、`parameterTypes`、`returnType`、`version`，
   并且**必须同时带上 `assessmentTestCases`**（切换模式时要重新校验参数个数）。

注意：`POST /api/v1/assessment-problems/import` 只做新增，不按标题或 ID 更新。
对已有题库重复导入会生成一批新题目，原来的考核仍然指向旧题目，请不要用它做“覆盖”。
导入请求现在也接受 `judgeMode`、`functionName`、`parameterTypes`、`returnType`，
可以直接导入函数式新题。
