## 1. 项目目标与范围

建设学院科创空间的管理系统，按学习方向管理学生，通过日报、周报记录学习过程，由大模型辅助评分并累计积分，展示个人在方向内和整个科创空间中的排名，落实连续14个完整自然日未提交日报的自动移出规则，并允许学院管理员恢复学生。月度评定和月度末位淘汰已取消。

本期覆盖人员管理、日报、周报、AI 评分、积分流水、排行榜、连续14个完整自然日未提交日报自动移出和管理员恢复，以及支撑上述流程的权限和审计。不包含考勤打卡、课程教学、项目审批、竞赛报名、奖励兑换或复杂教务系统对接。

### 1.1 用户已明确的需求

| 编号 | 需求 |
| --- | --- |

| U-02 | 学生提交日报，描述今天学了什么、学习收获等；至少获得 1 分，由大模型按内容质量评定 1–3 分并累计。 |

### 1.2 文档约定

- “已明确”指上述已确认的业务要求。
- “建议默认”指为使流程可执行而提出的方案，需学院确认后才能成为正式规则。
- “待确认”指尚无业务答案的事项，不得在开发时自行视为已确认。
- 本文描述业务需求及已确认的接口文档要求；框架版本、数据库、大模型厂商及部署细节由技术设计进一步明确。

## 2. 角色与权限

学生添加权限已明确属于学院管理员和方向负责人；其余权限划分为建议方案。

| 角色 | 权限 |
| --- | --- |
| 学院管理员 | 可添加全部方向的学生；建议同时管理全部方向和人员，查看报表和积分，复核评分，并恢复符合条件的学生。 |
| 方向负责人 | 仅可添加获授权方向的学生；可管理该方向人员、查看该方向报告与积分、查看排行榜并提出复核请求；本人不计入积分排行，也不提供“我的排名”；不得修改全局规则或越权访问其他方向的报告。 |
| 学生 | 不得自行注册或创建学生账号；建议可维护允许修改的个人信息，提交和查看自己的日报周报，查看自己的积分流水与排行榜。 |

建议以不可重复的内部成员 ID 关联数据，以学号作为业务唯一标识；登录方式待确认。人员管理与登录账号管理应区分，创建人员档案本身不应隐式赋予管理员权限。

学生可查看排行榜中的必要展示信息，但不能读取其他学生的学号、联系方式或报告全文。具体可见字段由学院确认。

## 3. 人员管理

### 3.1 方向管理

首期预置以下七个方向，分别统计人员、日报周报与积分排名：

1. AI 全栈。
2. 鸿蒙。
3. 网络安全。
4. C++。
5. 大数据。
6. 人工智能。
7. 项目创意设计。

建议首期每位学生只归属一个方向。是否允许多方向、方向新增或更名，属于待确认事项。

### 3.2 人员信息

| 字段 | 说明 |
| --- | --- |
| 成员 ID | 系统生成，稳定且唯一。 |
| 学号 | 必填，唯一，避免重复创建同一学生。 |
| 姓名 | 必填。 |
| 所属方向 | 必填，选择预置方向。 |
| 专业、班级、年级 | 建议采集，是否必填待确认。 |
| 联系方式 | 可选；仅有权限的管理人员可见。 |
| 加入时间 | 判断新成员观察期及未提交日报时长的依据。 |
| 成员状态 | 建议为在籍、已移出；报告处理状态与成员状态分别存储。 |
| 移出信息 | 移出时间、原因、触发规则及操作来源。 |
| 累计积分 | 由积分流水计算，创建人员时为 0，不直接编辑；自动移出时通过冲正流水清零。 |

### 3.3 增删改查

- 新增：仅学院管理员或获授权的方向负责人可在管理端添加学生；方向负责人只能添加到其负责的方向。校验必填字段与学号唯一性，新成员初始 0 分，记录操作人及加入时间。
- 查询：按方向、姓名、学号、班级、状态筛选，支持分页，查看人员详情与报告提交情况。
- 修改：按权限修改人员信息，方向变更记录原方向、新方向、生效时间和操作人。
- 删除：本期不提供管理员手动提前移出；满足14个完整自然日规则时由系统自动移出，不物理删除报告、积分流水或审计。
- 恢复：仅学院管理员可恢复学生，记录原因并开启新的在籍周期；历史报告和流水保留，净积分清零。

建议成员移出后不能提交新报告，也不进入在籍排行榜；管理员仍可查阅历史记录。账号是否允许只读登录属于待确认事项，至少必须撤销其在籍成员权限。

### 3.4 方向调整

报告保留提交时方向，当前排行榜按成员当前方向分组。方向调整不得改写历史报告；恢复后的新观察期从恢复时间开始。

### 3.5 学生账号创建与注册限制

学生档案及对应学生账号必须由所属方向负责人或学院管理员添加，学生不能通过用户端手动注册。学生端仅提供登录，不提供自行注册页面或入口；后端不得开放学生自注册接口，也不得在首次登录时自动创建尚未由管理人员添加的学生账号。

管理端添加接口必须校验角色及方向权限，普通学生和未登录用户不能调用；方向负责人不能通过修改请求中的方向或角色字段，跨方向添加学生或赋予管理权限。创建记录须包含操作人、所属方向和创建时间。

账号添加后的初始登录凭据、激活方式或学院统一认证账号绑定方式仍待确认，但不得变成学生自行注册流程。

## 4. 日报管理

### 4.1 日报内容与流程

日报建议包括报告日期、今天学习的内容、学习收获、遇到的问题、下一步计划，以及可选的代码或成果链接。学习内容与收获必填，其余字段可选。

学生保存草稿后可正式提交；草稿不计分，也不视为提交日报。正式提交必须通过内容非空、身份、成员状态及日期校验，提交成功后生成报告记录、评分任务和积分关联关系。

### 4.2 建议默认规则

- 每位学生每个自然日最多有一篇正式日报；唯一约束为成员 ID 与报告日期。
- 首期仅允许提交当天日报，不允许补交或选择未来日期；补交政策待确认。
- 正式提交后立即给予保底 1 分，AI 评分成功后按最终 1、2 或 3 分补足差额。
- AI 待处理、超时或失败不影响“已提交日报”的认定。
- 首期允许修改当天报告并留存版本；修改不产生第二笔保底分，必要时重新评分并按差额调整。
- 已跨日或已结算月份的报告默认只读，管理员复核走独立流程。
- 不提供学生自行删除已计分报告的入口；管理员作废报告时必须冲正积分，并明确它是否仍构成有效提交。

**积分解释：建议日报最终总分为 1–3 分，而不是“基础 1 分再额外加 1–3 分”。** 例如 AI 评定 3 分时，先获得的 1 分加后续 2 分，共 3 分。该解释需学院确认。

### 4.3 非法与重复内容

空白、纯符号、明显无意义文本不满足正式提交条件。内容相似或重复时可以提示管理员复核，但首期不建议仅凭 AI 判断自动作废或移出成员。最少字数、有效内容标准及举报处理方式待确认。

## 5. 周报管理

周报用于总结本周学习，建议包括本周学习概况、主要成果与收获、问题与反思、下周计划，以及可选成果链接。

建议以北京时间周一 00:00 至周日 23:59:59 为一个自然周，每位学生每周最多一篇正式周报，只允许在该周内提交；具体提交窗口及是否允许下周补交待确认。系统应保存明确的周期起止日期，不仅保存“第几周”。

建议周报也采用正式提交先入账 1 分、AI 完成后按最终 1–3 分调整的流程。该保底方案是对原始周报要求的补充，需要学院确认。

周报重复提交、修改、评分失败与作废机制参照日报。周报与日报分别计分，不互相替代；提交周报不能重置连续未提交日报的计时。

## 6. AI 自动评分

### 6.1 评分标准

| 分数 | 日报建议标准 | 周报建议标准 |
| --- | --- | --- |
| 1 分 | 满足有效提交要求，描述了学习事项，但过程或收获较少。 | 完成本周学习概述，但总结、成果或反思较少。 |
| 2 分 | 学习内容具体，能说明过程、收获或问题，有一定反思。 | 能结构化总结学习，说明主要收获、问题及下一步计划。 |
| 3 分 | 内容具体且可信，体现实践、问题解决与深入反思，可用成果证据支撑。 | 能综合分析本周实践与进展，复盘问题，并给出可执行的下周计划。 |

评分主要衡量学习记录的具体性、过程与成果、反思质量及计划可执行性，不简单按字数、专业术语数量或排版评分。不得因为不同方向、初学者身份或未提供外部链接而直接降低分数。

### 6.2 接入与可靠性

- 后端调用大模型，API 密钥不得下发浏览器。
- 模型输入仅包含评分所需的报告、类型和评分规则，默认不传姓名、学号、联系方式。
- 返回结构化结果：整数分数 1–3、简短评分理由；后端必须校验类型与范围。
- 报告正文属于不可信输入，不能覆盖评分规则，也不能授权模型执行其他操作。
- 记录报告版本、模型标识、评分规则版本、任务状态及时间，便于复核。
- 设置超时、有限重试和调用频率限制；失败保留保底分并进入待复核队列。
- 接收过期报告版本的结果时不更新当前分数；重复任务或重复回调不得重复加分。
- 保存原始模型输出时限制访问并纳入数据保留策略，不在日志中输出密钥或完整个人资料。

### 6.3 人工复核

建议学生可以对评分提出复核请求，由学院管理员确认最终分数，记录原分数、新分数、原因和处理人。人工覆盖后，迟到的 AI 结果不得覆盖人工结果。首期人工修正仍限定在 1–3 分，不包含额外奖惩积分；额外奖惩作为后续需求单独确认。

## 7. 积分与排行榜

### 7.1 积分原则

- 每位学生初始累计积分为 0。方向负责人可继续获得并保留报告积分，但不计入排行榜。
- 正式日报与周报各自贡献最终 1–3 分。
- 累计积分等于所有有效积分流水的净和，不能通过直接改写总分制造无法追踪的变化。
- 学院管理员可通过专用接口直接增加学生积分；只接受正整数，不要求原因、版本或幂等键。每次调用新增一条 `MANUAL_ADJUSTMENT` 流水并累计，不支持减分。
- 每条流水记录成员、关联报告、变化值、来源、操作时间和业务生效时间。
- 重评分、人工复核及报告作废只新增差额或冲正流水，不删除旧流水。
- 保存报告与积分采用事务或可恢复的一致性机制，避免“有报告无积分”和重复入账。

建议以报告首次正式提交时间作为该报告积分的业务生效时间，AI 后续补分仍归属原提交月份。周报跨月时也按首次提交月份归属。成员自动移出后，迟到评分不得新增积分。

### 7.2 排行榜

提供全空间排行榜、方向内排行榜、学生个人排名与积分流水；建议同时提供累计积分榜和指定月份积分榜。排行榜、排名人数和名次计算仅包含 `ACTIVE` 学生。方向负责人和学院管理员不进入总榜、方向榜或个人排名；方向负责人仍可查看榜单并使用自己的积分流水。移出成员通过历史记录查询。

显示名次、姓名或授权展示名、方向、积分；学生可以看到自己的总排名和方向排名。方向负责人端隐藏“我的排名”，个人首页不展示排名卡片；总榜和方向榜仍可查看。累计榜与月榜必须明确标注，不能混用。前端不得自行过滤负责人行，后端必须保证响应 `items`、`total`、rank 和同分计算均只统计学生。

建议相同积分并列，采用竞赛排名，例如 10、10、8 分对应名次 1、1、3。稳定展示排序使用成员 ID 等不影响名次的字段，不能据此触发任何自动移出。

## 8. 连续14个完整自然日未提交日报自动移出与恢复

### 8.1 已确认规则

- 仅 `ACTIVE` 学生参与自动移出；方向负责人和学院管理员不参与。
- 业务日期使用 `Asia/Shanghai`。当前正在进行的自然日不算完整日。
- 加入日或恢复日不计入完整日数量。
- 当前在籍周期的活跃基准日为最新一份正式提交日报的 `firstSubmittedAt` 所在自然日；从未提交时为 `membershipStartedAt` 所在自然日。
- 只有 `SUBMITTED` 日报重置计时。草稿、周报、评分结果和积分变化均不重置。
- 恢复前的日报不得延长恢复后的观察期。
- 基准日之后连续14个已经结束且无正式日报的自然日达到后，在第15个自然日开始时移出。

示例：2026-10-01 加入或最后提交日报，2026-10-02 至 2026-10-15 为14个完整自然日，2026-10-16 00:00 后的检查可执行移出。

### 8.2 自动移出

- 定时任务按配置周期检查，单成员事务、幂等执行；重复运行不得重复审计或重复冲正。
- 成员状态更新为 `REMOVED`，记录 `removedAt= TWO_WEEKS_NO_DAILY_REPORT` 和规则版本。
- 撤销该学生全部现有会话并递增认证版本，之后不能继续登录或提交。
- 历史报告、原始积分流水、冲正流水和审计全部保留，不物理删除。
- 自动移出时为每条非0原始积分追加等额 `REVERSAL`。成员总分、每份报告净得分和历史月份净积分归0，但原始积分记录仍可追溯。
- 移出后的迟到 AI 结果标记旧任务为 `STALE`，不得重新增加积分。
- 自动任务失败应记录安全审计并在下一周期补跑；不得静默漏检。

### 8.3 学院管理员恢复

- 学院管理员通过 `POST /api/v1/members/{memberId}/restore` 恢复 `REMOVED` 学生。
- 请求使用 `Idempotency-Key`、当前 `version` 和长度5–1000的 `reason`。
- 仅 `REMOVED` 学生可恢复；`ACTIVE` 成员、方向负责人和其他角色拒绝。
- 恢复将 `membershipStartedAt` 重置为当前业务时间，开始新的14个完整自然日观察期。
- `joinedAt`、报告、原始积分流水、冲正流水和审计保留；净积分保持0，新报告从0开始累计。
- 不恢复旧 token、旧 refresh family 或先前会话；`app_user.status` 保持原值。
- 再次满足不活跃条件时允许再次自动移出。

### 8.4 明确取消

不实施月度评定、月度淘汰人数、保护名单、同分淘汰、月度规则快照、确认、执行和月度任务。月度积分榜仅用于查询，不触发移出。手动提前移出学生也不在本期范围。

| 使用者 | 页面 | 核心操作 |
| --- | --- | --- |
| 学生 | 个人首页 | 查看方向、积分、总排名、方向排名和日报周报状态。 |
| 学生 | 日报、周报 | 保存草稿、提交、查看评分及理由、允许范围内修改、提出复核。 |
| 学生 | 排行榜、积分记录 | 切换方向或总榜、累计或月份，查看个人积分来源。 |
| 方向负责人 | 积分记录、排行榜 | 查看自己的积分流水和公开榜单；不展示“我的排名”或排名卡片。 |
| 管理人员 | 人员管理 | 筛选、分页、新增、查看、修改；管理员恢复被自动移出的学生。 |
| 管理人员 | 报告管理 | 按方向、学生、日期、类型、评分状态查看报告并复核。 |
| 学院管理员 | 成员恢复 | 查看自动移出依据，恢复符合条件的学生并保留审计。 |
| 学院管理员 | 自动任务与审计 | 查看评分失败、未提交提醒、移出任务及管理员操作记录。 |

首期建议提供响应式 Web 管理端和学生端，覆盖电脑与手机浏览器；独立 App、小程序、单点登录不在当前范围内。

## 10. 关键数据对象

| 对象 | 必要信息或约束 |
| --- | --- |
| 方向 | 标识、名称、启用状态。 |
| 人员与在籍周期 | 学号唯一、方向、角色、状态、加入或恢复时间、移出时间。 |
| 日报 | 成员、报告日期、提交时方向、内容、版本、首次提交时间；成员与日期唯一。 |
| 周报 | 成员、周期起止日期、提交时方向、内容、版本、首次提交时间；成员与周期唯一。 |
| 评分任务 | 报告版本、规则版本、模型、状态、分数、理由、重试次数；最终结果关联当前有效版本。 |
| 积分流水 | 成员、报告、增减值、来源、操作时间、业务生效时间、去重标识。 |
| 成员恢复记录 | 操作者、成员、原因、版本、恢复时间和新观察期起点。 |
| 成员资格变更 | 原状态、新状态、原因、触发任务、操作人及时间。 |
| 通知与审计 | 接收人、事件、发送状态，以及敏感操作的前后值与原因。 |

以上为逻辑数据需求，非最终数据库表设计。报告提交、评分入账、成员移出与月份结算须具备幂等性；同一个业务事件重试不能产生重复业务结果。

## 11. 非功能需求

### 12.1 安全与隐私

- 后端强制执行权限和方向隔离，不能只依赖前端隐藏按钮。
- 学生账号创建仅对获授权的管理人员开放；不提供公开自注册接口，方向负责人不得跨方向添加学生。
- 登录凭据安全存储，密码不可明文保存；传输采用 HTTPS。
- 报告展示防止脚本注入，登录、提交和模型调用具备合理限流。
- API 密钥、令牌及真实学生数据不得进入 Git 仓库。
- 自动移出不等于物理删除；数据保存多久、谁可查看、何时清除须由学院明确。
- 在接入外部模型前确认报告数据能否发送、模型侧保存策略及所需告知流程。此项是上线前业务确认条件，不作为未经核实的法律结论。

### 12.2 可靠性与可维护性

- AI 评分异步处理，不阻塞正式报告提交。
- 定时任务记录执行状态，支持失败告警、人工补跑和暂停。
- 关键流程记录规则版本，规则调整默认对后续周期生效，不无提示地追溯修改历史。
- 提供数据库备份与恢复方案，恢复时避免重放任务重复计分或重复移出。
- 系统时间存储与时区转换保持一致，报告日期与评定月份按业务时区计算。

### 12.3 体验与性能

常规列表采用分页；提交成功、待评分、评分失败、已移出等状态应清晰显示。学生端适配手机屏幕。

人数规模、峰值并发、页面响应时限、可用性和备份恢复指标暂未提供，需要在技术设计前确认，不将未经验证的性能数字作为既定承诺。

### 12.4 接口文档与前后端联调

后端使用 Knife4j 提供接口文档展示及在线调试能力，以 OpenAPI 3 描述接口契约。文档应随实际已实现的接口同步更新，覆盖接口名称、HTTP 方法与路径、请求参数、字段类型与必填约束、响应结构、HTTP 状态及错误说明；认证实现后补充认证方式和角色、方向权限要求。

开发环境提供 Knife4j 文档页面及 OpenAPI JSON，方便前端查看和调试；不为文档展示伪造尚未实现的业务接口。接口调试遵循与普通请求相同的认证和权限校验，不能绕过学生添加或方向隔离规则。

生产环境默认关闭文档页面及 OpenAPI JSON，文档示例不得包含真实学生数据、密码或有效令牌。具体依赖版本和 Spring Boot 兼容方案见后端技术设计，接入后必须验证页面及资源加载、文档生成和调试能力。

## 12. 验收标准

以下分为已确认需求验收与建议方案验收；带“建议”的行为须先确认相应规则。

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| AC-01 | 学院管理员或获授权的方向负责人创建学生并分配至允许管理的方向。 | 创建成功、初始 0 分，方向筛选可查到该成员，创建人及创建时间可追溯。 |
| AC-02 | 重复学号新增或修改信息。 | 拒绝重复学号，合法修改留痕，未授权操作被拒绝。 |
| AC-03 | 正式提交有效日报，AI 最终评定 3 分。 | 按建议方案先入账 1 分、后补 2 分，最终仅获得 3 分。 |
| AC-04 | 提交周报，AI 最终评定 2 分。 | 按建议方案该周报总贡献 2 分，与日报分别累计。 |
| AC-05 | 重复请求、重复评分回调或再次修改同一报告。 | 不新增第二份周期报告，不重复计分，只调整必要差额。 |
| AC-06 | AI 超时、返回 4 分、非整数或格式错误。 | 非法评分不入账，保留建议的 1 分及有效提交状态，进入重试或复核。 |
| AC-07 | 同一成员日报获 3 分、周报获 2 分，无其他流水。 | 累计 5 分，个人流水、方向榜和总榜数值一致。 |
| AC-08 | 存在同分成员。 | 按建议方案同分并列；同分只影响展示名次，不触发自动移出。 |
| AC-09 | 查询月度积分榜。 | 仅展示积分，不生成淘汰名单、不改变成员状态。 |
| AC-10 | 自动移出任务重复执行或服务重启后补跑。 | 同一学生只移出一次、只写一条审计和一组冲正，不重复撤销或加分。 |
| AC-11 | 2026-10-01 为最后日报，之后 14 个完整自然日无日报。 | 按建议口径在 2026-10-16 检查中移出，原因和依据可查。 |
| AC-12 | 2026-10-01 加入且从未提交日报。 | 2026-10-16 00:00 后的检查移出；加入日和未结束日期不计入。 |
| AC-13 | 期间仅提交周报，或日报已提交但评分失败。 | 周报不重置日报计时；有效日报提交不受评分失败影响。 |
| AC-14 | 学生被移出，管理员查看历史记录。 | 在籍权限撤销、不能新提交、不再进入在籍榜；报告和原始流水保留，净积分为0。 |
| AC-15 | 学生读取他人报告或方向负责人访问未授权方向。 | 后端拒绝访问，排行榜不泄露学号和联系方式。 |
| AC-16 | 提交成功与自动移出并发、服务中断后任务补跑。 | 执行前核验最新状态，不错误移出，不重复入账或通知。 |
| AC-17 | 旧报告版本 AI 结果或人工复核后的迟到结果返回。 | 不覆盖当前有效评分；差额与最终积分保持一致。 |
| AC-18 | 自动移出后迟到 AI 结果返回。 | 任务标为STALE，不新增积分，成员净积分保持0。 |
| AC-19 | 学生或未登录用户尝试自行注册或调用添加接口；方向负责人尝试跨方向添加或赋予管理权限；未添加的学生尝试首次登录。 | 学生端无自注册入口，后端不提供自注册能力；未授权添加、跨方向添加和越权赋权均被拒绝，首次登录不自动创建学生账号。 |
| AC-20 | 在开发环境访问 Knife4j 查看和调试已实现接口，再检查生产环境文档入口。 | 开发环境页面、资源及 OpenAPI JSON 正常加载，接口参数与响应说明匹配实现，调试不绕过权限；生产环境默认无法访问文档页面或 OpenAPI JSON，示例不泄露真实数据或有效凭据。 |
| AC-21 | 学生与方向负责人获得相同报告积分后查询总榜、方向榜和个人排名。 | 排行榜仅返回学生，排名人数、同分名次和分页 total 不包含负责人；负责人积分与流水仍保留，但前端不展示“我的排名”。 |

## 13. 上线前必须确认的问题

1. 日报最终 1–3 分的解释是否正确，还是基础 1 分加额外评分？周报是否采用提交保底 1 分？
2. 是否允许日报周报补交、跨日修改，以及请假、节假日或新成员豁免？
3. 一名学生能否加入多个方向？
4. 登录方式采用学号密码、学院统一认证，还是其他方式？管理人员添加学生后，初始登录凭据、激活或账号绑定如何处理？学生不可自行注册的规则已确认。
5. 历史报告、流水和审计保存多久？自动移出后的账号是否永久禁止登录？
6. 学院现有的大模型服务、可用预算、报告外发政策和通知渠道是什么？
7. 学生人数、同时使用规模、部署环境、备份及恢复目标是什么？

## 14. 建议开发顺序

1. 确认业务规则、角色权限、身份认证和数据隐私边界。
2. 实现人员与方向管理、日报周报提交和可追溯积分流水。
3. 接入 AI 评分、失败重试、人工复核与排行榜。
4. 实现14个完整自然日自动移出、积分冲正和管理员恢复。
5. 完成边界日期、并发、幂等、权限、恢复和迟到评分测试，并验证Knife4j契约。

本文不包含实施排期；待需求确认后另行形成技术设计和开发计划。
